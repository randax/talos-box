# 2. Issue #497 — durable Linux fallback daemon launch

## Decision

Use a transient systemd **service**, not `--scope`:

```text
systemd-run --user
  --unit=talos-box-tbxd-fallback-<caller-pid>.service
  --collect
  --service-type=exec
  --slice=app.slice
  --quiet
  [forwarded environment]
  --
  /absolute/path/to/tbxd
```

Run it synchronously with `exec.Command(...).Run()`. A transient service is launched by the user manager, with the manager as parent, and `systemd-run` returns once execution begins. A `--scope` command remains a child of `systemd-run` and is synchronous, which would retain an unnecessary wrapper process. This matches [systemd-run’s documented service/scope distinction](https://man7.org/linux/man-pages/man1/systemd-run.1.html).

This is only safe when user lingering is enabled. Moving into `user@UID.service` does not by itself survive the last logout: without lingering, the user manager and its units are stopped. Therefore:

- Linux + functioning user systemd + `Linger=yes`: launch through the transient service.
- Linux + `Linger=no`, unavailable `loginctl`, unavailable user bus, unavailable `systemd-run`, or non-systemd init: refuse; never fall back to a raw fork.
- WSL2 follows the same rule. This fixes terminal-session teardown but does not claim to survive `wsl --shutdown`, a Windows reboot, or WSL utility-VM termination.
- macOS retains the existing detached `setsid` fork. launchd installations remain unaffected because an active launchd daemon is reached through its existing socket/supervision path.

Use a unique unit name containing the caller PID. This avoids stale-name and concurrent-start collisions. `--collect` removes the transient unit after `tbxd` exits. Do not add the transient name to packaged-unit supervision detection: `tbx system restart` may continue to terminate the `tbxd` process it spawned; the transient unit then becomes inactive and is collected.

Forward only environment variables that alter daemon behavior:

- `PATH`
- `TBX_HELPER_SOCKET`, if set
- `TBX_BALLOON_RESERVE_MIB`, if set
- `TBXD_K8S_WARNINGS`, if set

Do not copy the whole CLI environment into the user service.

# 3. Issue #498 — pressure-aware ballooning and reboot observability

## Design decisions

### Shared macOS memory sample

Introduce one neutral internal probe so balloon and host-pressure code consume the same `vm_stat`/sysctl sample rather than duplicating parsers.

### Balloon policy

Do not subtract compressor bytes directly from free memory. Doing so would turn an 8 GiB compressor into an artificial 8 GiB deficit and induce the very guest reclaim pressure implicated in the panic.

Instead:

1. Base reclaim remains:

```text
max(0, reserveMiB - availableMiB)
```

2. Ignore new aggregate reclaim deficits below **256 MiB**.
3. Apply a new aggregate target at most once every **60 seconds**.
4. Treat compressor/swap/kernel pressure as a **release veto**:
   - It does not create reclaim by itself.
   - Once memory has been reclaimed for a real ≥256 MiB deficit, high pressure prevents the manager from giving that memory back merely because free+inactive+speculative briefly crosses the reserve.
5. Pressure latching:
   - Arm when any condition is true:
     - swap used ≥80%;
     - compressor ≥20% of physical RAM;
     - kernel pressure is warning or critical.
   - Clear only when all are true:
     - swap used <70%;
     - compressor <15% of RAM;
     - kernel pressure is neither warning nor critical.
   - If total RAM is unavailable, use an absolute compressor fallback: arm at 4 GiB, clear below 3 GiB.
6. The pre-balloon hold bypasses both the 256 MiB deadband and rate limit. A 1 MiB admission hold must remain valid because existing #398 tests intentionally cover tiny shortfalls.
7. A failed target application does not consume the 60-second rate-limit window.

This directly prevents the 2–88 MiB target flap in the issue while retaining balloon response to real deficits.

### Reboot detection

Use the authenticated Talos `MachineService.SystemStat` call and compare its nonzero `boot_time` value. The v1.13 machinery API already exposes `SystemStat.boot_time` as a typed field; see the [Talos API reference](https://docs.siderolabs.com/talos/v1.12/reference/api).

Treat `boot_time` as an opaque boot identity; UI timestamps should use when `tbxd` observed the change, not reinterpret the raw value.

- Poll cadence: reuse the existing daemon stall watcher’s **30-second** cadence.
- First successful observation establishes a baseline and is not a reboot.
- A changed nonzero value for the same running VM is a reboot.
- Deliberate `tbx` starts/restarts clear the baseline via `recordVMStart`; they must not be reported as unexpected guest reboots.
- Log exactly once per changed value.
- Expose `PhaseRebooted = "rebooted"` for **15 minutes** after detection, then return to `configured`.
- Add `rebootedAt` to `NodeStatus` JSON.
- A daemon restart loses the in-memory baseline; document this limitation.
- Missing Talos credentials or a failed SystemStat call skips reboot classification; the existing credentials/service warning remains the remediation.

Reboot observation is cross-platform. Only the macOS host-pressure and balloon sample is platform-specific.

### Swap warning

Add a steady-state advisory at **swap used ≥80%**:

- It is always `SeverityWarn` by itself.
- Existing warning/critical-pressure rules may still escalate to `SeverityBlock`.
- No duplicate findings: if the existing memory finding already includes swap, return one combined finding.
- `tbx doctor` always reports it.
- Table-form `tbx status` reports it when at least one returned cluster is running.
- JSON status remains unchanged except for per-node reboot fields, matching the existing table-only offline-mode banner precedent.

# 4. Issue #499 — path-prefixed catch-all mirror routing

## Decision

Accept:

```text
/v2/<upstream-authority>/<repository>/...
```

Examples:

```text
/v2/public.ecr.aws/docker/library/golang/manifests/1.25-alpine
/v2/xpkg.crossplane.io/crossplane/provider-aws/manifests/v1.0.0
/v2/registry.example:5443/team/app/blobs/sha256:...
```

The first segment after `/v2/` is an upstream authority only if it contains `.` or `:`. This avoids interpreting ordinary repository roots such as `library`, `docker`, or `team` as hosts.

Authorities continue through `parseUpstreamAuthority`; no new validation or cache namespace is introduced.

Precedence:

1. `/v2/` remains the namespace-free registry ping.
2. If a nonempty `?ns=` is present, it wins and the path remains unchanged. This preserves containerd exactly, even if the first repository segment contains a dot.
3. Without `ns`, inspect the first segment:
   - contains `.` or `:`: parse as authority and strip it before forwarding;
   - otherwise: retain the existing 400 `missing ns query parameter`.
4. A host-only path such as `/v2/public.ecr.aws/` is 400 because no repository/API operation follows it.
5. Other query parameters are preserved; only `ns` is removed on the legacy query route.
6. GET and HEAD remain allowed; writes remain 405 before route parsing.

IPv6 bracketed authorities and explicit ports use the existing parser. Use `EscapedPath`/`PathUnescape` for the single authority segment and reject a decoded `/`; never normalize an encoded slash into the repository path.

# 5. Issue #500 — phase-aware bootstrap hint

## Decision and gating rule

Keep the hint for substrate-only/manual clusters, but suppress it on positive evidence that bootstrapping has already progressed:

```go
showManualBootstrap :=
    allNodesConfigured &&
    !provisioning &&
    !status.KubernetesReady &&
    !anyHealthyKubelet(status.Nodes)
```

`anyHealthyKubelet` returns true when any node has:

```go
node.Kubelet != nil &&
node.Kubelet.Health == ServiceHealthHealthy
```

Any node counts, not only the control plane. A healthy kubelet is sufficient evidence that repeatedly suggesting `talosctl bootstrap` is unsafe and stale.

Do not infer health from:

- `PhaseConfigured` alone;
- a nil/unavailable service probe;
- `starting`, `unknown`, `unhealthy`, or `crashlooping` kubelet;

# 7. Open questions and risks

These do not block implementation but must be validated before merge:

- `loginctl enable-linger` may be policy-restricted on some distributions. The chosen behavior is still refusal, never raw fork.
- WSL user-bus instability can make `systemd-run --user` fail despite systemd PID 1. The refusal must name the packaged socket setup and not imply that `setsid` is safe.
- Verify the transient service lands in `app.slice` on Ubuntu 22.04, Ubuntu 24.04, Fedora, and current WSL. The explicit `--slice=app.slice` should make this deterministic.
- Verify Talos `SystemStat.boot_time` stays constant across NTP corrections and suspend/resume. If the live gate disproves that, the pre-merge fallback is the authenticated MachineService `Read` API for `/proc/sys/kernel/random/boot_id`; do not ship a known-unstable reboot identity.
- Reboot detection requires an exact talosconfig context. Without credentials, only apid phase remains observable; status must not fabricate a reboot.
- A daemon restart cannot identify a reboot that happened before it established its first baseline.
- The 15-minute `rebooted` visibility window is intentionally transient; the durable evidence is `tbxd.log`.
- Compressor thresholds are policy numbers, not macOS kernel contracts. Keep them named constants and log every decision input so future tuning is evidence-driven.
- Docker host-side testing may require insecure-registry daemon configuration. `crane --insecure` and direct HTTP tests are the required acceptance path; Docker is additional live compatibility evidence.
- Path-prefix routing intentionally excludes single-label authorities without a port. Such registries retain `?ns=` support or can use `name:port`.
